## Domain Analyst

### Domain
Text classification of customer feedback with a bring-your-own LLM (self-serve SaaS)

### Dynamics
- The feedback arrives as unstructured text that the user pastes in by hand. Entries vary a lot: a short "love it!" may sit next to a long, mixed-sentiment complaint. Nothing says whether entries come one at a time or in bulk.
- The user connects "a language model of their choice", so output quality, response time and cost depend on whichever provider they pick. The same input can be labeled differently by different models, or by the same model on different runs.
- The value builds up over time. One classified entry is not very useful. The dashboard "breakdown by sentiment and category" only becomes meaningful once many entries are stored.
- Categories depend on the business: one company's "billing" is another's "pricing". The submission does not say whether categories are fixed, user-defined or chosen by the model.
- A typical day for the user is probably: paste in a batch from a support inbox, survey or review site, then look at the dashboard for shifts in sentiment. This is inferred, not stated.

### Constraints
- **Budget and team:** $100–500/mo, 4 weeks, 1 developer. LLM inference costs are paid by the user through their own model connection, not by the app's budget.
- **Data sensitivity:** customer feedback can include personal information such as names, emails and order numbers. That text is sent to a third-party model and stored in Postgres. No regulatory regime (GDPR or similar) is mentioned, but it could apply depending on who the users are.
- **Credential handling:** "connect a language model" implies storing user API keys or endpoints, which is a security concern.
- **Platform limits:** Vercel serverless function timeouts constrain how long LLM calls can run.
- No cultural constraints are stated.

### Who benefits
- **Primary:** the person who triages feedback (product manager, support lead or founder at a small company). They save time on manual tagging and get a rolled-up view.
- **Secondary:** decision-makers who look at the dashboard to decide priorities without reading every entry.
- **Indirect:** the end customers whose feedback gets noticed and acted on sooner.
- The submission does not say who the target user is, whether solo users or teams, or which industry.

### What downstream personas should pay attention to
Labels from a user-chosen model are non-deterministic and the category set is undefined, so the dashboard is only as reliable as the classification is consistent. The other personas should treat the category scheme and output consistency across providers as open questions before scoping.

## Scope Architect

### Executive summary
Small teams get customer feedback from many places and have no fast way to see what customers are saying overall. V1 is a self-serve web app. A user signs in, connects their own language model, and pastes in feedback. The app labels each entry with a sentiment and a category, writes a one-line summary, stores the result, and shows a dashboard that rolls up all entries over time.

### In scope (V1)
- A user can sign in with a magic link sent to their email. Each user sees only their own data.
- A user can connect one language model: pick a provider from a short supported list, enter an API key or endpoint, and test the connection before saving.
- A user can replace or remove their saved model connection at any time. The stored key is never shown back in full.
- A user can paste a single feedback entry and submit it for analysis.
- A user can paste several entries at once (one per line, or separated by a clear delimiter) and have each one analyzed and saved separately.
- Each analyzed entry gets exactly one sentiment from a fixed set (positive / neutral / negative / mixed).
- Each analyzed entry gets exactly one category from a fixed default list (e.g. bug, feature request, pricing/billing, usability, support, praise, other). The model must choose from this list and cannot invent new labels.
- Each analyzed entry gets a summary of no more than about 25 words.
- Each saved entry stores the original text, sentiment, category, summary, the model used, and a timestamp.
- If the model fails or returns output in the wrong format, the user sees a clear error and nothing broken is saved. The user can retry.
- A user can manually correct the sentiment or category of any saved entry.
- A user can delete a single entry.
- The dashboard shows how many entries fall under each sentiment and each category.
- The dashboard shows the most recent entries with their labels and summaries.
- The dashboard can be filtered by a simple date range (e.g. last 7 / 30 / all days).
- Visits to the public landing page are tracked with Plausible.

### Out of scope (V1, deliberate)
- **User-defined or editable categories:** they make labels inconsistent, which undermines the dashboard. A fixed list keeps the breakdown meaningful.
- **Teams, workspaces or shared dashboards:** V1 targets one person doing the triage, and sharing adds permissions complexity.
- **Automatic ingestion (email, Zendesk, Intercom, app-store or survey integrations):** each integration is its own project. Pasting proves the core value first.
- **CSV/file upload and export:** pasting multiple entries covers bulk input for V1, and export can follow once the data model is stable.
- **Large batch or background processing of hundreds of entries:** serverless timeouts make this risky, so batches are capped at a modest size.
- **Trend charts over time, alerts or anomaly detection:** these need lots of stored history first. Counts plus a date filter are enough to start.
- **Comparing models or running several models on the same entry:** this is interesting, but it serves evaluation rather than triage.
- **App-hosted or free-tier model access:** inference costs stay with the user, which protects the $100–500/mo budget.
- **Automatic PII redaction:** this is a hard problem to do reliably. V1 shows a clear notice that pasted text is sent to the user's chosen provider.
- **Billing, subscriptions or usage plans:** these aren't needed to prove value and would cut into the 4-week timeline.
- **Multi-language tuning or translation:** the app accepts whatever the model handles, with no extra language-specific work.

### Why these boundaries
The Domain Analyst flagged that the dashboard is only as trustworthy as the labels behind it. Because the model is chosen by the user and can label the same text differently, V1 limits that variation with a fixed set of sentiments, a fixed category list, strict output checking, and manual correction. Everything else that's left out (integrations, teams, trend analysis, bulk pipelines) only adds value once single-user paste-and-classify works reliably. With one developer, four weeks and serverless time limits, V1 keeps to that core loop: paste, classify, store, see the breakdown.

## Impact Quantifier

### Who benefits
- **Feedback triager (PM, support lead or founder at a small company)** · Spends less time hand-tagging and summarizing pasted feedback · Spends less time per batch and no longer keeps a tagging spreadsheet
- **Decision-makers who read the dashboard** · See sentiment and category counts without reading every entry · Planning conversations cite "X% negative, mostly billing" instead of anecdotes
- **End customers** · Recurring complaints get noticed sooner · Fewer repeat reports of the same issue (a lagging signal that we can't measure directly)
- **The operator (AiNa/demo)** · Gets a public-URL reference SaaS that proves bring-your-own-LLM classification works · Live deployment, signups, retained users

### Magnitude estimate
The AIR gives **no numbers**. Every bracket below needs validation.
- **Manual triage cost:** about 30–90 seconds per entry to read, tag and summarize. Automated, it's about 5–10 seconds (paste plus model latency). At 50–300 entries a week, that saves **roughly 0.5–5 hours/week per triager**. *Needs validation.*
- **Time to insight:** goes from "whenever someone builds the spreadsheet" (days to weeks) to **immediately after pasting**. *Needs validation.*
- **Cost to the user:** BYO model, so inference is about **$0.0001–0.002 per entry** on small models, or near zero on local Ollama. That is negligible next to an hour of triager time. *Needs validation per provider.*
- **Operator cost:** fits within the **$100–500/mo** band because inference is paid by the user (Scope: "inference costs stay with the user").

### Evidence we have
- The pain statement itself: *"have the model classify its sentiment and category and write a short summary… a dashboard should show how feedback breaks down by sentiment and category."* This shows the job exists, but not how much it costs today.
- Constraints: *"budget $100-500 · 4w · team 1"*, which bounds what we spend, not the value delivered.
- Domain Analyst: *"The value builds up over time. One classified entry is not very useful."* Impact depends on sustained use, not one-off trials.
- Domain Analyst: *"The submission does not say who the target user is."* The magnitude can't be anchored to a persona yet.

### Evidence we'd need
- **Volume:** how many feedback entries does a target user handle per week? Is it under 50, 50–500, or more? This decides whether the time saved is trivial or meaningful.
- **Current process:** do they tag manually today, use a spreadsheet, use a helpdesk's built-in tags, or not do it at all? If they don't do it at all, the value is new insight, not time saved, and the pitch changes.
- **Time per entry today:** measure it on a real batch of 20 entries.
- **Label accuracy threshold:** what share of manual corrections would make them stop trusting the dashboard (10%? 25%)?
- **Who reads the dashboard:** the triager alone, or someone above them? This determines whether the secondary benefit exists.
- **Willingness to bring a key:** will target users really paste an API key? If they won't, adoption drops sharply.

### Measurement plan (post-launch)
1. **Label correction rate:** manual corrections ÷ entries analyzed. Target **<15%** over 30 days. Above 25% means the dashboard isn't trustworthy.
2. **Retained active usage:** share of users who connect a model and then analyze entries in **≥3 separate weeks out of their first 6**. Target **≥30%**. This is the test of the "value builds up over time" claim.
3. **Throughput per session:** median entries analyzed per paste session and median seconds from paste to saved result. Target **≥10 entries/session** and **<10 seconds per entry**. Combined with the validated manual time per entry, this lets us calculate hours saved.

Supporting signals: Plausible landing-to-signup conversion, and the share of signups who successfully test a model connection. The second one is the main drop-off risk.

## Longevity Critic

### 3-year outlook
By late 2029, sentiment and category tagging of feedback will be a free, built-in feature of most helpdesk, CRM and survey tools. Zendesk, Intercom, HubSpot and Productboard already ship AI tagging in some form. LLM inference will be cheap enough that nobody thinks about its cost. This project bets that a standalone, paste-based, bring-your-own-model tool keeps a niche. It bets against the platforms' native features getting good enough that small teams never leave the tool where their feedback already lives.

### Defensibility
**Very little, honestly.** The core loop is: a prompt with a fixed list of labels, a call to the model, a database row, and two counts. A competent developer can rebuild it in a weekend, and an LLM coding agent in an afternoon. A fixed category list and manual correction are good product choices, but they don't protect it. Two things could become defensible later, and both are out of scope for V1:
- **Accumulated, user-corrected label history.** This could be used to fine-tune prompts per user or to set accuracy baselines for each model.
- **Integrations.** These are where feedback actually lives, and integrations are what make a tool sticky.

That's fine for a reference SaaS that proves bring-your-own-LLM classification works. It isn't fine if it's meant to be a business on its own.

### Market drift risks
1. **Incumbents bundle it (fast).** Helpdesks and survey tools already offer AI tagging and summaries, and they are spreading it to cheaper tiers. If the target user is on Intercom or Zendesk, they will never paste text into a separate app.
2. **General chat assistants absorb the task (fast).** Someone can paste 50 entries into ChatGPT or Claude and ask for a table with a sentiment breakdown. Assistants with memory, projects and built-in charts make "persistent storage plus dashboard" the only real difference, and that difference is getting smaller.
3. **Model churn breaks label consistency (fast).** Providers retire models every 6–12 months. A user's dashboard can quietly shift when "gpt-x-mini" is swapped for its successor, and V1 records the model used but doesn't flag that kind of drift.
4. **Regulation of personal data in LLM pipelines (slow).** EU AI Act transparency rules, GDPR enforcement on sending customer text to third-party models, and US state privacy laws could make "paste raw customer text to your provider" a compliance blocker for B2B buyers.

### Kill criteria
- **Activation:** if fewer than 30% of signups successfully test a model connection by week 8 after launch, pause. Bring-your-own-key is the barrier to entry, and it would mean the barrier is fatal.
- **Retention:** if fewer than 20% of activated users analyze entries in ≥3 of their first 6 weeks (target was 30%) by month 4, stop building features and rescope toward integrations or kill the project.
- **Trust:** if the label correction rate stays above 25% across the median user for 60 days, the dashboard is unreliable. Stop and fix classification before adding anything else.

### Verdict
**Yellow.** Ship it as scoped, because 4 weeks, one developer and a public URL make it a cheap, honest experiment. Go in with two named caveats:
- It has essentially no moat against bundled AI tagging and general chat assistants.
- Its long-term value depends on becoming the place feedback flows *into*, through integrations and correction-driven accuracy, rather than a box people paste into. Decide by month 4 whether it's heading there.

## Dependency Mapper

### Data dependencies
- **Pasted customer feedback:** the user owns it, but their own customers wrote it, and it may contain names, emails or order IDs. The app has no say in its quality, language or how consent was obtained.
- **User LLM credentials:** each user supplies their own API keys or endpoints. These are high-value secrets and need encryption at rest, plus a plan for key rotation and revocation.
- **Model outputs:** labels are generated by a third party and can vary between runs. Dashboard accuracy depends on output we neither control nor version.
- **User email addresses:** magic-link sign-in collects them. They are personal data in their own right.
- **No seed or benchmark dataset exists** to check that classification works across providers. Someone has to source or write sample feedback.

### Partner / vendor dependencies
- **Vercel (hosting):** runs the app and the serverless functions. If Vercel is down, the whole app is down. The Hobby plan bans commercial use, so expect Pro at about $20/mo per seat.
- **Managed Postgres (Neon, Supabase or Vercel Postgres):** stores all persistent data. An outage means nothing can be saved and the dashboard is empty. Cost is $0–25/mo at this scale.
- **Transactional email provider (Resend, Postmark or SES):** magic links depend on delivery. If it fails or links go to spam, nobody can sign in. Cost is $0–20/mo.
- **LLM providers (OpenAI, Anthropic, Google, Mistral and others):** do all the classification. Users pay for usage, but provider outages, rate limits, model retirements and API changes surface as our bugs.
- **Ollama / self-hosted endpoints:** the repo history shows Ollama support. A serverless function on Vercel can't reach `localhost`, so this only works if users expose their endpoint publicly.
- **Plausible:** landing-page analytics only, so an outage doesn't hurt the product. Cost is about $9–19/mo.
- **Domain registrar and DNS:** needed for the public URL and for email-sending reputation (SPF, DKIM). Cost is about $15/yr.

### Regulatory / compliance
- **GDPR / UK GDPR:** applies if any users or their customers are in the EU or UK. The operator is probably a *processor* for feedback data and a *controller* for account data. That requires a DPA, a privacy policy, deletion and export handling, and disclosure of sub-processors.
- **Cross-border transfer:** customer text goes to whichever LLM provider the user picks, possibly outside the EU. The user has to own that decision, so the notice and terms must make it explicit.
- **CCPA/CPRA and US state privacy laws:** apply to Californian users and similar. They require a privacy policy and handling of deletion requests.
- **EU AI Act:** sentiment tagging is low-risk, but the transparency duties for AI-generated content are worth noting in the UI.
- **HIPAA, KYC/AML and age verification:** don't apply unless healthcare users paste PHI. The terms should prohibit that.
- **Provider terms of service:** some LLM terms limit using their output in competing products or reselling access. Bring-your-own-key keeps us mostly clear, but this should be checked.
- **Email law (CAN-SPAM, PECR):** magic-link emails are transactional, so the risk is low.

### Distribution dependencies
- **Public URL plus organic discovery only.** There's no app store, embed partner or content review to get through. That also means no built-in reach.
- **No acquisition channel is defined.** Launch traffic would have to come from Product Hunt, Hacker News, indie communities or the operator's network, and none of these is confirmed.
- **Activation depends on users already having an API key.** Non-technical PMs and support leads may not have one or be allowed to use one.
- **Getting magic-link emails into the inbox** is a hidden gate to sign-up. A new sending domain with no reputation is likely to land in spam.

### Critical path callouts
1. **Users' willingness and ability to bring a working LLM key.** If most target users lack a key, or can't expose a local endpoint like Ollama to Vercel, the product can't be activated. Confirm the target persona and the providers they actually use before building.
2. **Data-handling posture for third-party customer text.** If early B2B users ask for a DPA, a sub-processor list or EU data residency, a 4-week single-developer build with no compliance work will stall. Agree with the customer up front on target region and how sensitive the data is.
3. **Vercel function timeouts vs. LLM latency.** Slow models, or pasting several entries in one request, can go over the serverless time limits and break the core loop. Confirm the plan tier and maximum batch size early.

## Variant Designer

### Variant 1: Lean (tier_lean)

**Budget band (USD):** 20 - 60
**Engineer-weeks:** 2.5
**Ops complexity:** low
**Recommended stack family:** nextjs-app-router+vercel-hobby-to-pro+neon-postgres+shadcn+resend
**Target scale:** "1–50 users, single operator per account"

The budget band is the monthly running cost. It does not include engineer time. This variant has one Next.js app on Vercel. Each submit makes one synchronous API call (`app/api/analyze/route.ts`) that sends a single entry to the user's model. Data lives in Neon free or Launch tier through Drizzle. Magic links go through Auth.js with Resend. Two providers are supported: OpenAI and Anthropic, plus any OpenAI-compatible endpoint. API keys are encrypted with AES-GCM using one environment-held key. The dashboard has two shadcn bar charts and a list of the 20 most recent entries. Plausible tracks the landing page only.

**Tradeoffs:**
- Fits easily in 4 weeks and leaves about 1.5 weeks of buffer for magic-link email delivery and provider quirks.
- Single entries only. A "batch" is just the browser sending entries one at a time, so there's no server-side batching and no timeout risk.
- No manual label correction and no date filter. Both are in Scope, so this cuts V1 scope.
- Only one encryption key and no rotation plan. Acceptable at demo scale.
- Gives up the correction-rate metric that the Impact and Longevity kill criteria depend on.

**Kill criteria:**
- The operator needs the label-correction metric to make the month-4 decision. Lean doesn't collect it.
- Early users paste 20+ entries at a time and the one-by-one flow feels broken.

### Variant 2: Recommended (tier_recommended)

**Budget band (USD):** 45 - 120
**Engineer-weeks:** 4
**Ops complexity:** medium
**Recommended stack family:** nextjs-app-router+vercel-pro+neon-postgres+shadcn+resend+zod-structured-output
**Target scale:** "50–500 users, ~10k entries/month"

The budget band is monthly: Vercel Pro $20, Neon $0–25, Resend $0–20, Plausible $9–19, plus domain. Engineer time is not included. This variant covers the full Scope Architect V1. Provider adapters cover OpenAI, Anthropic, Gemini and OpenAI-compatible endpoints, including Ollama on a public URL. Ollama on `localhost` is documented as unsupported. There's a "Test connection" step. Model output is checked against a zod schema with fixed sentiment and category enums, retried once, and nothing is saved if it still fails. Batches are capped at 25 entries. The client runs them with concurrency 3 and shows progress for each entry. Users can correct and delete entries, and each correction is logged so the correction rate can be measured. The dashboard has a 7/30/all-days filter. Saved keys show only their last 4 characters. The app also ships a privacy notice, terms that ban PHI, and account deletion.

**Tradeoffs:**
- Delivers all of V1 Scope plus the three Impact metrics: correction rate, retention and throughput.
- Uses the whole 4-week budget with no slack. Slippage most likely comes from provider adapters and email deliverability.
- Client-side batching avoids needing a queue, but closing the tab stops the batch partway through.
- Basic GDPR hygiene (privacy policy, deletion), but no DPA and no EU data residency.

**Kill criteria:**
- The target buyers are B2B teams that require a DPA or sub-processor list before trying the product.
- The typical paste is more than 100 entries, which needs real background processing.
- Fewer than 30% of signups manage to test a model connection by week 8.

### Variant 3: Hardened (tier_hardened)

**Budget band (USD):** 150 - 450
**Engineer-weeks:** 8
**Ops complexity:** high
**Recommended stack family:** nextjs-app-router+vercel-pro+neon-postgres+inngest-or-qstash+kms-envelope-encryption+sentry
**Target scale:** "500–5,000 users, B2B pilots, 100k+ entries/month"

The budget band is monthly. Engineer time is not included. This variant has everything in Recommended, plus:
- Durable background jobs (Inngest or Upstash QStash) for batches of up to 500 entries, with retries and resume.
- Envelope encryption of API keys through AWS KMS, with rotation.
- Per-user rate limits.
- Sentry for errors, and an audit log.
- Model-drift flags that warn when the model behind a dashboard range changes.
- CSV import and export, plus data export for GDPR.
- A seed benchmark set to check accuracy for each provider.
- A drafted DPA and sub-processor page, with an EU-region Neon option.

**Tradeoffs:**
- Ready for B2B pilots and large pastes, and covers the Longevity "model churn" risk.
- Takes **about twice the stated 4-week timeline** with one developer. It doesn't fit the AIR constraints.
- More vendors means more points of failure and more monthly cost.
- Puts heavy investment into a product the Longevity Critic rates **Yellow**, with almost no moat.

**Kill criteria:**
- The timeline stays fixed at 4 weeks with one developer.
- There's no confirmed B2B pilot that needs compliance or high volume.
- Activation and retention haven't been validated on a cheaper variant first.

### Recommended variant: tier_recommended

It is the only variant that delivers the full V1 scope and the measurements the month-4 go/kill decision needs while staying inside 4 weeks, one developer and the $100–500/mo budget, though with no schedule slack.

### Open questions / risks

- **Budget meaning:** is $100–500 a monthly running budget, as the Braindoc says, or the total build budget? One developer for 4 weeks costs far more than $500 in labor. Ideation needs to know which.
- **Bring-your-own-key activation:** do the target users actually have API keys, and which providers do they use? Local Ollama won't work from Vercel unless the endpoint is public. This is the biggest adoption risk.
- **Data posture:** which regions are users in, and will early users ask for a DPA or EU residency? If yes, parts of Hardened move into scope.
- **Batch size and latency:** what is the realistic paste size? A cap of 25 with client-side concurrency works only if typical batches are small. Confirm whether the Vercel plan is Pro.
- **Strategic direction:** Longevity says long-term value depends on integrations and correction-driven accuracy. Decide now whether V1 is a reference demo or the first step toward a product. That changes how much to invest past Recommended.
