## Domain Architect

### Architectural posture
This is one Next.js App Router monolith on Vercel Pro, built web-first for desktop triage. Per **tier_recommended**, every model call is synchronous and handles **one entry per request**. Batching (up to 25 entries, 3 at a time) runs in the browser, so V1 needs no queue or worker tier. Analysis is request/response. The dashboard reads directly from Postgres, so no realtime layer is needed.

### Tech stack
The BuildSpec fixes this stack. Stack Selector picks the libraries within it.
- **Runtime / framework:** Node, Next.js App Router. Route handlers go under `app/api/*`.
- **Database:** Postgres (Neon managed, as the variant suggests).
- **UI:** shadcn/ui, with simple bar charts for the breakdowns.
- **Hosting:** Vercel. Config is `vercel.json` with no Dockerfile. It needs a per-route `maxDuration` on the analyze and test-connection routes.
- **Capabilities:** magic-link auth and Plausible on the landing page only.
- **Variant additions:** zod structured-output validation and one transactional email provider for sending magic links.

### Data shape (high-level)
The data is mostly **tabular records** with low cardinality:
- users
- one encrypted model connection per user
- feedback entries: raw text, sentiment enum, category enum, summary, model id, timestamps
- an append-only label-correction log, which the correction-rate metric needs

Raw text runs from short to medium length and may contain PII. Dashboard queries are `GROUP BY` counts over a date range, plus a "latest N" list.

### Integration footprint
1. **LLM providers (outbound):** OpenAI, Anthropic, Gemini, and OpenAI-compatible endpoints (including Ollama on a public URL)
2. **Transactional email:** magic links (Resend/Postmark)
3. **Managed Postgres:** Neon
4. **Plausible:** a script tag on the landing page
5. **DNS / SPF / DKIM:** needed for both the public URL and email deliverability

There are no inbound webhooks, no payments and no SSO in V1.

### Latency / scale ceiling
- **Primary action (paste → saved entry):** under 10 s p50 per entry, with a hard cap around 60 s per function call. That allows one retry on output that fails validation, with headroom for slow models.
- **A 25-entry batch:** about 1–2 min wall-clock, shown with per-entry progress.
- **Dashboard:** under 1 s.
- **V1 ceiling:** 50–500 users and about 10k entries a month (around 330 a day). Postgres handles this easily. The real limits are provider rate limits on each user's own key and Vercel function duration.

### Non-obvious constraint
**Calling "OpenAI-compatible endpoints" means the server fetches a URL the user supplied (an SSRF risk).** The "Test connection" step and every analyze call make server-side requests to whatever base URL the user saved. Without guards, someone can use the app to probe internal or private addresses, or make it hang on a slow endpoint. Required guards:
- HTTPS only
- resolve DNS and reject private, loopback and link-local ranges
- strict timeouts
- no redirect following
- never send other users' credentials

The same check is also why `localhost` Ollama should fail fast with a clear "expose a public URL" message instead of timing out.

A related point for the Data Modeler and prompt design: OpenAI-compatible and local models often ignore JSON-schema or tool-call modes. Plan for prompt-level JSON, then normalize enums (case, spaces, `feature request` vs `feature_request`), then validate with zod. Treat native structured output as an optimization, not something every provider supports.

## Stack Selector

### Chosen variant
**tier_recommended**: 4 engineer-weeks, about $45–120/mo, built for 50–500 users and around 10k entries a month. It is the only variant that covers the full V1 scope and logs label corrections, which the month-4 go/kill decision needs. The stack has no worker tier or queue, so one engineer can build it in 4 weeks.

### Backend
- **Language + framework:** TypeScript 5.x on Node 22 LTS, using Next.js 16 App Router route handlers (`app/api/analyze`, `app/api/connection/test`) and Server Actions.
- **Persistence:** Neon Postgres 17 through Drizzle ORM and `drizzle-kit` migrations, with the `@neondatabase/serverless` driver.
  - **Tables:** `users`, `model_connections`, `feedback_entries`, `label_corrections` (append-only), plus the Auth.js tables.
  - **Encryption:** API keys are encrypted with AES-256-GCM using Node `crypto` and a `KEY_ENCRYPTION_SECRET` environment variable. Each row stores a `key_version` column so the key can be rotated later.
- **LLM layer:** Vercel AI SDK 5 with `@ai-sdk/openai`, `@ai-sdk/anthropic`, `@ai-sdk/google` and `@ai-sdk/openai-compatible`.
  - Calls use `generateObject` against a zod 4 schema where the provider supports it. Otherwise the prompt asks for JSON, which the app parses, normalises and re-checks with zod.
  - A failed check gets one retry, and nothing is saved if the retry also fails.
- **SSRF guard:** a custom `fetch` is passed to the openai-compatible provider. It:
  - only allows HTTPS
  - looks up the host with `dns.lookup` and rejects private, loopback and link-local addresses (checked with `ipaddr.js`)
  - sets `redirect: "manual"`
  - aborts after 45 s via `AbortSignal.timeout(45_000)`
- **Background work:** none. Batches of up to 25 entries run in the browser, 3 at a time (`p-limit`).
- **Why:** The BuildSpec fixes Next.js and Postgres. Drizzle is light, typed and works well on serverless. The AI SDK gives one interface for four providers, so the app doesn't need its own adapter for each.

### Frontend
- **Approach:** server-side rendering with React Server Components. The dashboard is fetched on the server, and the paste and batch screen is a client component.
- **Framework + libraries:**
  - React 19 and shadcn/ui
  - shadcn Charts (Recharts) for the sentiment and category bar charts
  - TanStack Table for the latest-entries list
  - react-hook-form with zod for forms
  - sonner for toasts
- **Styling:** Tailwind CSS v4.
- **Why:** shadcn is in the BuildSpec. RSC lets the dashboard's `GROUP BY` queries run on the server with no separate API to maintain.

### Hosting / deployment
- **Where:** Vercel Pro. The Hobby plan doesn't allow commercial use.
  - `vercel.json` sets `maxDuration: 60` on the analyze route and `30` on the test-connection route.
  - No Dockerfile.
- **Database hosting:** Neon Launch plan, with a database branch for each preview deployment.
- **CI/CD:**
  - GitHub Actions runs typecheck, lint, Vitest and a `drizzle-kit check`.
  - Vercel's Git integration deploys each branch to a preview and `main` to production.
  - Migrations run in a production deploy step.
- **Monthly cost at 50–500 users:**

  | Item | Cost |
  |---|---|
  | Vercel Pro | $20 |
  | Neon | $0–19 |
  | Resend | $0–20 |
  | Plausible | $9–19 |
  | Domain | ~$1 |
  | **Total** | **~$45–80/mo** |

  This sits well under the $100–500 budget. Users pay for their own model calls.

### Auth
- **Mechanism:** magic-link sign-in with session cookies. Sessions are stored in the database through the Drizzle adapter.
- **Provider:** Auth.js v5 (`next-auth@5`) with its Resend email provider.
  - Resend sends from a verified domain with SPF, DKIM and DMARC set up.
  - Magic links are rate-limited per email address with a simple Postgres counter.

### Skipped on purpose
- **Inngest / QStash background jobs:** batches are capped at 25 and run in the browser. These belong to tier_hardened.
- **Clerk / Supabase Auth:** an extra vendor and per-user pricing for something Auth.js does for free with tables we already own.
- **Prisma:** its client is heavier and starts slower on serverless than Drizzle, which gains nothing here.
- **LangChain:** too much abstraction for one call that returns structured output. The AI SDK already handles it.
- **AWS KMS envelope encryption:** an AES-GCM key held in an environment variable, plus a `key_version` column for later rotation, is enough at this scale.

## Data Modeler

### Entities

All ids are `uuid` with `default gen_random_uuid()` unless noted. Enums are Postgres enums declared with Drizzle `pgEnum`:
- `sentiment`: `positive | neutral | negative | mixed`
- `category`: `bug | feature_request | pricing_billing | usability | support | praise | other`
- `provider`: `openai | anthropic | google | openai_compatible`
- `label_field`: `sentiment | category`

**users** (Auth.js Drizzle adapter shape)
- id: text · Auth.js user id · PK
- email: text · login identity · unique, not null
- email_verified: timestamptz · set on first magic-link use · nullable
- created_at: timestamptz · signup time, needed for retention cohorts · not null, default now()

**sessions** (Auth.js)
- session_token: text · cookie value · PK
- user_id: text · owner · FK to users, on delete cascade
- expires: timestamptz · not null

**verification_tokens** (Auth.js)
- identifier: text · email · not null
- token: text · hashed magic-link token · not null
- expires: timestamptz · not null
- composite PK (identifier, token)

**magic_link_attempts**
- email: text · normalized lowercase · PK (email, window_start)
- window_start: timestamptz · start of the rate-limit bucket (e.g. hourly)
- count: integer · sends in this window · not null, default 1

**model_connections**
- id: uuid · PK
- user_id: text · owner · FK to users, on delete cascade, **unique** (one per user)
- provider: provider · not null
- model_id: text · e.g. `gpt-4o-mini`, `llama3.1` · not null
- base_url: text · HTTPS only, checked by the SSRF guard · nullable (required when provider = openai_compatible)
- api_key_encrypted: text · AES-256-GCM, `iv:tag:ciphertext` in base64 · nullable (keyless Ollama)
- key_version: smallint · which `KEY_ENCRYPTION_SECRET` encrypted it · not null, default 1
- key_last4: text · shown in the UI · nullable
- last_tested_at: timestamptz · last successful "Test connection", used for the activation metric · nullable
- created_at / updated_at: timestamptz · not null

**feedback_entries**
- id: uuid · PK
- user_id: text · owner · FK to users, on delete cascade
- raw_text: text · pasted feedback, may contain PII · not null, CHECK length ≤ 10 000
- sentiment: sentiment · current label (after any correction) · not null
- category: category · current label · not null
- summary: text · ≤ ~25 words · not null
- provider: provider · snapshot at analysis time · not null
- model_id: text · snapshot, not a FK, so it survives connection changes · not null
- created_at: timestamptz · analysis time, used by the dashboard date filter · not null
- updated_at: timestamptz · last correction · not null

**label_corrections** (append-only, never updated)
- id: uuid · PK
- user_id: text · FK to users, on delete cascade
- entry_id: uuid · FK to feedback_entries, **on delete set null** · nullable
- field: label_field · not null
- old_value: text · label before the correction · not null
- new_value: text · label after the correction · not null
- created_at: timestamptz · not null

### Relationships
- A user has many sessions, at most one model connection, many feedback entries and many label corrections.
- A feedback entry belongs to one user and has many label corrections.
- A label correction belongs to a user. It points to an entry while that entry exists.
- Feedback entries don't reference model connections: provider and model are copied onto each entry, so replacing or removing a connection never changes past data.
- Deleting a user cascades to all of their rows. Deleting a single entry keeps its correction rows (with entry_id set to null), so the correction-rate metric still counts them.

### Indices that matter for V1
1. **`feedback_entries (user_id, created_at DESC) INCLUDE (sentiment, category)`**: one index serves the latest-N list, the 7/30/all-day filter, and both `GROUP BY` counts as index-only scans.
2. **`label_corrections (user_id, created_at)`**: for the correction-rate metric over a time window.
3. **`users (email)` unique** and **`magic_link_attempts` composite PK**: fast lookups during sign-in and rate limiting.

### Migration strategy
Generate SQL migrations with `drizzle-kit generate`, commit them, check them in CI with `drizzle-kit check`, and apply them in the production deploy step. Never edit an applied migration. Add enum values with forward-only `ALTER TYPE … ADD VALUE` migrations.

### Open questions for the customer
- **Deleted entries:** when a user deletes an entry, should its correction history stay as anonymous metric data (the current design), or does deletion have to remove every trace for GDPR?
- **Original labels:** is the correction log enough to recover the model's original labels, or do you want `model_sentiment` / `model_category` columns on each entry for easier accuracy reporting?
- **Category list:** is the 7-value list final? Renaming or removing a value later needs a data migration, while adding one is cheap.
- **Raw text retention:** should pasted text be purged after N days, or should the cap be lower than 10k characters? This affects both PII exposure and storage.
- **One connection per user:** is that firm for V1? Allowing several would mean dropping the unique constraint and adding a "default connection" flag.
- **Duplicate pastes:** should pasting the same text twice be blocked, for example with a content hash per user, or allowed?
- **Single-user data:** confirm there's no workspace or team concept in V1. Adding a tenant column later is a migration across every table.

## API Designer

### API contract summary
The API is a set of Next.js App Router route handlers under `app/api/*`, using the `[id]` dynamic-segment convention. They return JSON. The dashboard is a React Server Component, so it queries Postgres directly through Drizzle and needs no read API. Corrections and deletes use route handlers, not Server Actions, so the same contract can serve the TanStack table and scripts. There is no versioning. `vercel.json` sets `maxDuration: 60` on `/api/analyze` and `30` on `/api/connection/test`. All model calls handle one entry per request, and the browser runs batches with `p-limit(3)`, up to 25 entries.

### Route groups

```
## /api/auth  (Auth.js v5 catch-all: app/api/auth/[...nextauth]/route.ts)
POST   /api/auth/signin/resend     → send magic link (rate-limited via magic_link_attempts)
GET    /api/auth/callback/resend   → verify token, create session
POST   /api/auth/signout           → end session
GET    /api/auth/session           → current session

## /api/connection   (singular: one model_connections row per user)
GET    /api/connection             → fetch saved connection (key_last4 only, never the key)
PUT    /api/connection             → create or replace (encrypts key, SSRF-checks base_url)
DELETE /api/connection             → remove
POST   /api/connection/test        → test unsaved or saved credentials; sets last_tested_at on success

## /api/analyze
POST   /api/analyze                → classify ONE entry, save feedback_entries row

## /api/entries
GET    /api/entries                → latest N, ?range=7d|30d|all&limit=20&cursor=
PATCH  /api/entries/[id]           → correct sentiment and/or category (writes label_corrections)
DELETE /api/entries/[id]           → delete entry (corrections kept, entry_id → null)

## /api/stats
GET    /api/stats?range=7d|30d|all → sentiment + category counts (also used by RSC loader)

## /api/account
DELETE /api/account                → delete user + cascade (privacy requirement)
```

These are deliberately left out: entry creation outside `/api/analyze`, CSV import/export, a categories CRUD (the category list is a fixed enum), and team routes.

### Request / response shape (key endpoints)

```json
POST /api/connection/test
{ "provider": "openai_compatible", "model_id": "llama3.1",
  "base_url": "https://ollama.example.com/v1", "api_key": "sk-..." }
// api_key/base_url optional → falls back to saved model_connections row
→ 200 { "ok": true, "latency_ms": 840, "model_id": "llama3.1" }
→ 422 { "error": { "code": "ssrf_blocked", "message": "Private or localhost URLs can't be reached from the server. Expose a public HTTPS URL." } }
```

```json
POST /api/analyze
{ "raw_text": "Checkout keeps charging me twice…" }      // ≤ 10 000 chars
→ 201 FeedbackEntry
{ "id": "6f1c…", "raw_text": "…", "sentiment": "negative",
  "category": "pricing_billing", "summary": "User reports duplicate charges at checkout.",
  "provider": "openai", "model_id": "gpt-4o-mini", "created_at": "2026-10-21T09:12:00Z" }
→ 502 { "error": { "code": "model_invalid_output", "message": "Model output failed validation after 1 retry; nothing saved.", "retryable": true } }
```

```json
PATCH /api/entries/[id]
{ "sentiment": "mixed" }                 // and/or "category"
→ 200 FeedbackEntry (updated)            // one label_corrections row per changed field
```

```json
GET /api/stats?range=30d
→ 200 { "range": "30d", "total": 212,
        "sentiment": { "positive": 80, "neutral": 41, "negative": 77, "mixed": 14 },
        "category": { "bug": 52, "feature_request": 38, "pricing_billing": 30,
                      "usability": 29, "support": 25, "praise": 31, "other": 7 } }
```

The `PUT /api/connection` body has the same fields as the test request. Its response is the `ModelConnection` without the encrypted key: `{ id, provider, model_id, base_url, key_last4, last_tested_at }`.

### Auth requirements per endpoint
V1 has many users but no teams. Each request uses the Auth.js database-session cookie, and every query is scoped by `session.user.id`.

| Route | Auth |
|---|---|
| `/api/auth/*` | Public. Sign-in is rate-limited per email in `magic_link_attempts`. |
| `/api/connection`, `/api/connection/test` | Session required. Only the caller's own row is used. Another user's credentials are never loaded. |
| `/api/analyze` | Session and a saved connection required. A missing connection returns 409 `no_connection`. |
| `/api/entries`, `/api/entries/[id]` | Session required. Someone else's `[id]` returns **404**, not 403, so the endpoint doesn't reveal that the entry exists. |
| `/api/stats`, `/api/account` | Session required. |
| Landing, privacy and terms pages | Public, with the Plausible script tag. |

Mutating routes rely on Auth.js `SameSite=Lax` cookies and an `Origin` header check. There are no API tokens in V1.

### Error shape
Every error returns `{ "error": { "code": "snake_case", "message": "human readable", "retryable"?: boolean, "fields"?: { "<field>": "msg" } } }`. Status codes:
- 400: malformed JSON
- 401: no session
- 404: entry not found or not owned by the caller
- 409: `no_connection`
- 413: `raw_text` over 10k characters
- 422: zod validation failure (with `fields`), `ssrf_blocked` or `https_required`
- 429: magic-link rate limit, or `provider_rate_limited` passed through from the user's provider
- 502: `provider_error` or `model_invalid_output` (`retryable: true`)
- 504: `provider_timeout` (the 45 s abort)
- 500: unexpected failure, with a generic message only

Provider error bodies are never echoed back, because they can contain key fragments. The batch UI uses `retryable` to decide whether to show a retry button for each entry.

### Webhooks (in / out)
- **Inbound: none.** There are no payments or integrations in V1. The magic-link callback is a user's browser redirect, not a webhook.
- **Outbound: none.** The only outbound calls are synchronous requests to the user's LLM provider (through the SSRF-guarded fetch) and Resend's send API. Neither is a webhook.
- **Later (not V1):** Resend bounce/complaint webhooks at `POST /api/webhooks/resend` (Svix-signed, payload `{ type, data: { email_id, to } }`). These would let the app flag undeliverable sign-in emails once deliverability becomes a measured problem.

### User flows (golden paths)

**Flow: First run to first insight**
1. User on / → clicks "Sign in with email".
2. → /signin, enters email → opens the link from the inbox.
3. → no connection exists, so the app redirects to /connect.
4. → picks OpenAI, enters `gpt-4o-mini` and a key → clicks "Test" → "OK · 840 ms" → "Save".
5. → /analyze opens with focus in the textarea.

**Flow: Batch paste and classify**
1. User on /analyze → pastes 18 lines → the count shows "18 entries".
2. → clicks "Analyze" → each row goes pending → spinner → labeled.
3. → one row fails with `model_invalid_output` → user clicks "Retry" on that row → it saves.
4. → clicks "View dashboard" → /dashboard, where the counts include the new entries.

**Flow: Correct a wrong label**
1. User on /dashboard → sets the filter to 30d → spots "praise" on a complaint.
2. → changes the category select to `bug` → an optimistic update and a "Label updated" toast appear (the change is logged as a correction).
3. → the category chart updates after the page reloads its data.

## NFR Specialist

### NFR highlights
- V1 has many users but each user's data is isolated. Auth is a magic link plus a database session, and every query is scoped to `session.user.id`.
- The main risks are SSRF through user-supplied base URLs, and API keys stored at rest. The guard and AES-256-GCM encryption are V1 requirements, not optional extras.
- Performance is limited by the user's chosen model, not by our own code. One entry per request, with a 45 s abort and a 60 s Vercel `maxDuration`.
- Observability stays lean for this tier: structured logs, a health endpoint and Vercel's built-in monitoring. Sentry is deferred to tier_hardened.

### Auth + access
- **Who:** anyone with an email can sign up through a public URL. Each user sees only their own data, and V1 has no teams or roles.
- **Sessions:** Auth.js v5 database sessions with a 30-day sliding expiry. Cookies are `HttpOnly`, `Secure` and `SameSite=Lax`, and mutating routes also check the `Origin` header.
- **Magic links:** they expire after 10 minutes, work once, and are stored hashed. Sending is limited to 5 links per email per hour, plus a per-IP cap.
- **Password reset / MFA:** not needed, since there are no passwords. MFA is out of scope for V1.

### Performance budget
- **Primary action (paste → saved entry):** p95 under 15 s, mostly model time. Our own overhead (auth, database and validation) is p95 under 300 ms. The dashboard loads in p95 under 1 s.
- **Concurrent users:** 50 active at once, which is about 150 analyze calls in flight with 3 per user.
- **Row volume:** 250k `feedback_entries` without slowing down, which is about two years at roughly 10k a month. The covering index `(user_id, created_at DESC)` keeps dashboard counts as index-only scans.
- **Not optimizing:** batches over 25, mobile layout, cold starts, cross-region latency, or provider rate limits (those are the user's quota).

### Security baseline
- **Input validation:** every route body is checked with a zod schema. `raw_text` is capped at 10k characters (413 above that). Model output is parsed, its enums normalized, and then checked with zod again. All SQL goes through Drizzle with parameters, and React escapes output. Summaries are never rendered as HTML.
- **Secrets:**
  - Vercel environment variables (`KEY_ENCRYPTION_SECRET`, `AUTH_SECRET`, `DATABASE_URL`, `RESEND_API_KEY`), with production and preview scoped separately.
  - User API keys use AES-256-GCM with a `key_version` column. Only the last 4 characters are ever returned.
  - Keys and provider error bodies are never logged.
- **HTTPS:** Vercel-managed Let's Encrypt certificates and HSTS.
- **Risk 1: SSRF.** Only HTTPS is allowed. DNS is resolved and private, loopback and link-local ranges are rejected. Redirects are not followed, and requests abort after 45 s. The DNS check runs on every call, not only when the connection is saved, which guards against DNS rebinding.
- **Risk 2: prompt injection in pasted feedback.** Pasted text goes to the model as delimited user content. Output is limited to the enum and schema, so injected text can't create new labels or run actions.

### Privacy
- **Collected:** account emails, pasted customer feedback (which may contain third-party PII), model summaries and encrypted API keys.
- **Stored:** Neon Postgres in one US region. EU residency is deferred, as Variant Designer noted.
- **Leaves the environment:** feedback text goes only to the provider the user chose. The `/analyze` notice says so, as the Scope Architect required. Emails go to Resend. Plausible collects no personal data, has no cookies, and runs on the landing page only.
- **Controls:**
  - Account deletion cascades through all of the user's data.
  - Entries can be deleted one at a time.
  - The terms prohibit pasting PHI.
  - There is no DPA in V1, which is a known kill criterion for B2B buyers.

### Observability
- **Logs:** structured JSON lines to Vercel Logs, with `route`, `user_id`, `provider`, `latency_ms`, `error.code` and `request_id`. Raw text is never logged.
- **Error tracking:** none in V1. Vercel log drains and alerts are enough at this tier.
- **Health:** `GET /api/health` checks the database with `SELECT 1`, and an uptime monitor pings it.
- **Metrics:** SQL queries for correction rate, activation (`last_tested_at`) and retention. No metrics stack.

### Error handling philosophy
Each failure tells the user what went wrong, what to do next, and whether anything was saved. Provider failures appear on the affected row and name the provider, the cause (timeout, rate limit or invalid output) and whether retrying makes sense. Bad or incomplete model output is never saved. Field errors appear next to the field they belong to. Unexpected failures show a generic message with a `request_id`, and the full details are logged on the server.

### i18n / accessibility
- **i18n:** the interface is English only. Feedback in any language is accepted, and the model handles it as well as it can.
- **a11y:** the baseline is WCAG 2.1 AA:
  - Built on shadcn/Radix primitives, so everything can be reached by keyboard.
  - Focus is always visible.
  - Sentiment colors always have text labels next to them.
  - Batch row status updates use `aria-live`.
  - Charts have a table alternative.

### Cost-ceiling guardrails
- **LLM spend:** users bring their own keys, so the operator pays nothing for inference. To protect users' own bills, batches are capped at 25 entries, each call is limited to 1 entry plus 1 retry, and output is capped with `maxOutputTokens` at about 300.
- **Vercel function time:** the analyze route has `maxDuration: 60`, requests abort after 45 s, and there is a per-user cap of 500 analyze calls a day. Set a Vercel spend limit and Neon autoscaling limits so monthly costs stay under about $120.

### Elevator pitch
A self-serve web app where a small-team feedback triager connects their own language model, pastes customer feedback, and gets each entry labelled with a sentiment, a category and a short summary. Every entry is saved, and a dashboard shows the sentiment and category breakdown plus the latest entries.

### Chosen variant
`tier_recommended`

### Features

- **Magic-link sign-in** [P0]
  - what: Users sign in with an emailed one-time link through Auth.js v5 and Resend, using database sessions.
  - acceptance: (1) A link works once and expires after 10 min; a second use or an expired link is rejected. (2) The 6th send request for the same email within 1 hour returns 429. (3) Without a session, every `/api/*` route except `/api/auth/*` and `/api/health` returns 401.
  - depends on: users, sessions, verification_tokens, magic_link_attempts · `/api/auth/*` · /signin

- **Model connection (test → save)** [P0]
  - what: The user saves one connection (OpenAI, Anthropic, Gemini or an OpenAI-compatible endpoint) after a test passes. The key is encrypted at rest.
  - acceptance: (1) `PUT` stores the key with AES-256-GCM, and `GET` returns only `key_last4`, never the key or its ciphertext. (2) A `base_url` that is `http://`, `localhost`, or resolves to a private, loopback or link-local IP returns 422 (`https_required` / `ssrf_blocked`), and no outbound request is made. (3) A successful test sets `last_tested_at` and returns `latency_ms`. Redirects are not followed, and the request aborts at 45 s with 504.
  - depends on: model_connections · `/api/connection`, `/api/connection/test` · /connect

- **Analyze one entry** [P0]
  - what: The server classifies one pasted entry with the user's model and saves the labels, the summary, and a snapshot of the provider and model.
  - acceptance: (1) A valid call returns 201. Sentiment is from {positive, neutral, negative, mixed}, category is from the 7-value enum, and the summary is ≤ 25 words. (2) Output that is invalid or outside the enums (after normalising, e.g. `Feature Request` → `feature_request`) gets 1 retry. If the retry also fails, the route returns 502 `model_invalid_output`, `retryable: true`, and no row is written. (3) Text over 10,000 chars returns 413. With no saved connection the route returns 409 `no_connection`. The 501st call in a day for one user returns 429.
  - depends on: feedback_entries, model_connections · `/api/analyze` · /analyze

- **Batch paste (client-side)** [P0]
  - what: Up to 25 lines are each sent as a separate analyze call, 3 at a time, with a status on each row.
  - acceptance: (1) Pasting 26+ non-empty lines blocks submission and shows a cap message. (2) A failed row with `retryable` errors shows Retry, and the other rows still save. (3) If a batch is running, closing the tab triggers a `beforeunload` warning.
  - depends on: feedback_entries · `/api/analyze` · /analyze

- **Dashboard breakdown + latest entries** [P0]
  - what: Sentiment and category counts and the latest entries, filtered by 7d, 30d or all time.
  - acceptance: (1) `/api/stats?range=30d` counts include only the caller's entries from the last 30 days, and the counts sum to `total`. (2) `/api/entries` returns entries newest first with `limit` and `cursor` paging. (3) User A never sees User B's entries or counts.
  - depends on: feedback_entries · `/api/stats`, `/api/entries` · /dashboard

- **Correct labels** [P0]
  - what: The user edits an entry's sentiment and/or category, and each change is logged in an append-only table.
  - acceptance: (1) A PATCH that changes both fields writes 2 `label_corrections` rows with the correct old and new values. A PATCH that changes nothing writes 0. (2) A value outside the enum returns 422. (3) Patching another user's entry returns 404.

### User flows (golden paths)
1. **First run:** / → /signin → open the magic link → no connection exists, so redirect to /connect → pick a provider, enter model and key → Test (OK · latency) → Save → /analyze with focus in the textarea.
2. **Batch analyze:** paste 18 lines → counter shows "18 / 25" → Analyze → each row goes pending → labelled. One row fails with `model_invalid_output` → Retry → it saves → "View dashboard".
3. **Correct a label:** /dashboard → choose 30d → change a wrong category in the table → optimistic update and "Label updated" toast → the correction is logged and the chart updates when the data reloads.
4. **Remove data:** delete a row from the table, or go to /account → type the email to confirm → the account is deleted and the user is signed out.

### Data model summary
- **users / sessions / verification_tokens**: Auth.js identity and sessions.
- **magic_link_attempts**: rate-limit counter per email per hour.
- **model_connections**: one per user. Provider, model, base URL, encrypted key, `key_version`, `last4`, `last_tested_at`.
- **feedback_entries**: raw text, current sentiment and category, summary, provider and model snapshot, timestamps.
- **label_corrections**: append-only log of label edits, used for the correction-rate metric.

Full field detail is in the Data Modeler output.

### API contract summary
`/api/auth/*` · `/api/connection` (+ `/test`) · `/api/analyze` · `/api/entries` (+ `/[id]`) · `/api/stats` · `/api/account` · `/api/health`

Full shapes and the error envelope are in the API Designer output.

### NFR highlights
1. **SSRF guard on every outbound model call**, not only at save time: HTTPS only, the DNS result is checked against private, loopback and link-local ranges, no redirects, and a 45 s abort.
2. **Keys are never exposed:** AES-256-GCM with `key_version`. Only `last4` is returned, and keys and provider error bodies are never logged or echoed.
3. **Strict per-user scoping:** every query filters by `session.user.id`, and another user's resource returns 404.
4. **Nothing invalid is persisted:** model output goes through zod, enum normalisation and 1 retry, or the request fails. `maxOutputTokens` is about 300, and `maxDuration` is 60 on analyze and 30 on test.
5. **Lean observability:** structured JSON logs with `request_id`, and raw text is never logged.

### Open questions
1. **Budget:** is $100–500 the monthly run cost or the total build budget? *Default: monthly run cost (we estimate ~$45–80/mo).*
2. **Target users and providers:** do target users have API keys? *Default: OpenAI, Anthropic, Gemini and compatible endpoints. Localhost Ollama is unsupported.*
3. **Deleted entries:** should correction history stay as anonymised data? *Default: yes, `entry_id` is set to null.*

7. **Duplicate pastes:** should they be blocked? *Default: allowed.*

### What's NOT in V1 (deliberate)
- **Server-side or background batching:** no queue and no batches over 25. Closing the tab stops the batch.
- **User-defined categories, teams and shared workspaces:** single user, fixed enums.
- **Integrations and CSV import/export:** paste only.
- **Trend charts, alerts and model-drift detection:** counts plus a date filter only.
- **App-hosted inference, billing, PII redaction, DPA or EU residency:** a PII notice is shown on /analyze instead.
